# v1.5.1 — Reasoning-First Path + P0/P1/P2 Priority Classification (2026-08-04)

**User原话**: "推理最佳路径和最优解决方案, 直接全量开干"

**含义**: 当用户说 "推理最佳路径" 时, **推理要在实现之前**. 不要接到一个"做 X"的指令就立刻动 X — 先把 X 拆成 1-10 个子任务, 按 ROI 排序, 然后才有动作.

## 1. Reasoning-First Pattern (5 步)

任何 "做 X" / "升级 X" / "调优 X" 的请求, 在工具调用之前先输出 reasoning:

```
Step 1: 当前状态评估 (1-3 句话)
  - 当前算法/项目有什么
  - 哪些够用 / 哪些不够

Step 2: 候选方案枚举 (3-10 个)
  - P0 (高 ROI, 必修) — Impact × Confidence ÷ Effort
  - P1 (中 ROI, 应该做)
  - P2 (低 ROI, 可选)

Step 3: 跳过什么 + 为什么
  - 列出明显不做的 P2 项及理由
  - 用户可能质疑的项

Step 4: 推荐执行顺序
  - P0 全部 + P1 关键 + 跳过 P2
  - 预计产出 + 预计时间

Step 5: 一个 verify 该有的形态 (双轨 / 回归测试 / 产出等价)
```

**真实事件 (2026-08-04 同会话)**:
- 用户: "看看当前算法结构, 和 github 成熟的高 star 的生产级的活跃的项目进行对比, 看看有没有需要调优的地方"
- 接收立刻做: 不行, 因为没有 6 项目对比 + 没有 P0/P1/P2 分类 + 没有 60 天路线
- 一次性推理输出: 6 项目 + 35 指标 + P0 (3 项) + P1 (4 项) + P2 (3 项) + 跳过 P2 理由 + 60 天路线
- 用户: "继续" → 落地 P0+P1
- 用户: "推理最佳路径和最优解决方案, 直接全量开干" → 推理 → 跳过 P2 → 5 个 bridging OPT (OPT-8/9/10/11/12) → 107 tests 一次过

**关键信号 / 触发词**:
- "推理最佳路径" / "找最优方案" / "看有没有可调优的" / "找根因" / "对比业界"
- "和 github 成熟的高 star 的生产级的活跃的项目进行对比"
- 用户给出大方向但不指定具体做哪个 → 必须 reasoning 输出 P0/P1/P2

## 2. P0/P1/P2 Priority Classification

| 级别 | ROI | Effort | 触发标准 | 例子 |
|------|-----|--------|---------|------|
| **P0** | 高 | 小/中 | (1) 影响生产路径 + (2) < 1 天 + (3) 0 改动原代码 | Typed Signature (OPT-1), JSON Schema (OPT-2), pytest (OPT-3) |
| **P1** | 中 | 中 | (1) 升级算法质量 + (2) 1-3 天 + (3) 仍 0 改动原代码 | Sentence-transformers (OPT-4), Adaptive EWMA (OPT-5), Compiled state (OPT-6), Circuit breaker (OPT-7) |
| **P2** | 低 | 中/大 | (1) 锦上添花 + (2) > 3 天 + (3) 无直接用户价值 | Radix tree, structlog, LLM judge ensemble |

**P2 跳过示例 (3 项, 2026-08-04)**:
1. **Radix tree for instruction lookup** — 当前 N < 100, 线性扫描够用, SGLang 用是因为 N > 1M
2. **Structured logging** — print() 已够 debug, structlog 优化无用户价值
3. **LLM judge ensemble** — heuristic fallback 已够, Prometheus 是给学术 benchmark 用

**判定 P2 准则** (满足任一即跳过):
- 数据规模 < 阈值 (Radix tree N < 1K 没价值)
- 没有具体的 debug/tracing 痛点 (structlog)
- 没有精度回归风险 (judge ensemble 增加成本但精度差不多)

## 3. Bridging OPT (OPT-8..12) Pattern

**关键洞察**: P0 + P1 做完 ≠ 落地. 还需要 bridging OPT 把所有算法接到 production 路径:

```
P0/P1 = 7 个独立算法 (OPT-1 到 OPT-7)
Bridging = 5 个 集成层 (OPT-8 到 OPT-12):
  - OPT-8 integrated_runner: 默认 v2 + v1 fallback
  - OPT-9 downloader integration: chrome_batch_pdf_downloader_v15 自动用
  - OPT-10 perf benchmark: v1 vs v2 latency 对比
  - OPT-11 cross-device deterministic: 验证字节级一致
  - OPT-12 e2e integration: 真实 PDF 端到端测试
```

**Bridging OPT 的 5 个必备**:
1. **production wrapper** (integrated_runner) — 默认 OPT, 失败 fallback
2. **caller integration** (downloader v15) — 真实 caller 自动用 OPT
3. **performance benchmark** (bench.py) — 量化 v2 overhead
4. **deterministic verification** (cross-device tests) — 字节级一致
5. **end-to-end integration** (e2e tests) — 真实文件验证

**没有 bridging 会出现**:
- 算法存在但没人调用 → 0 价值
- 算法被无意调用 → 性能 regression
- 多次调用结果不一致 → 跨部署失败
- 真实环境里 fail → 才发现没测过

## 4. 跨设备 Deterministic 测试 (OPT-11)

**前提**: 算法驱动 = 算法 + 数据结构 + 状态序列化. 跨设备一致 = 同输入同输出.

**测什么**:
| 维度 | 验证 |
|------|------|
| 算法纯函数 | 多次调用浮点漂移 < 0.001 |
| Bayesian 决策 | β_mean 字节级一致 |
| Compiled state | JSON round-trip 等价 |
| Mirror picker | 多次调用结果一致 |
| State atomic write | 无 stale .tmp 文件 |
| Algorithm fail | state 仍 valid JSON (不 corrupt) |
| 主文件 md5 | 跨次调用一致 |

**陷阱**: 浮点 EWMA 累加, 100 次调用后漂移 ~3e-5. `pytest.approx(rel=1e-6)` 不够, 用 `abs(a - b) < 0.001`.

## 6. State Pollution After Demo (避免 regression)

**真问题 (2026-08-04)**: 跑 acceptance demo 会修改 state (mirror EWMA, circuit breaker, adaptive), 紧接着跑 test 失败.

**修法**: demo 跑完 → 重置 state → 跑 test

```python
# 1. 跑 demo (修改 state)
subprocess.run(['python3', '~/.medit/tests/acceptance_demo.py'])

# 2. 重置 state 到洁净 baseline
import json
from pathlib import Path
state = json.loads(Path('~/.medit/cache/mirror_health_state.json').read_text())
state['mirrors'] = {
    'sci-hub.ren': {'ewma': 0.83, 'samples': 3, ...},
    'sci-hub.ee': {'ewma': 0.5, 'samples': 0, ...},
    ...
}
Path('~/.medit/cache/mirror_health_state.json').write_text(json.dumps(state))

# 3. 跑 test
import subprocess
subprocess.run(['/bin/bash', '~/.medit/tests/run_all.sh'])
```

**这是 v1.5.0 acceptance 后必须做的 "reset state" 步骤**.

## 7. Pytest venv / system python mismatch

**真问题 (2026-08-04)**: 系统 `python3` (3.9.6 + pytest 8.4.2) vs hermes venv python (3.11.15 + pytest 9.1.0) 行为不同. 同一个 test 在 venv 跑过, 在系统 python 跑失败 (jsonschema enum 验证差异).

**修法**: `~/.medit/tests/run_all.sh` 硬编码 venv python:

```bash
#!/bin/bash
export PYTHONPATH="/Users/david/.medit/scripts:/Users/david/.medit/tests:$PYTHONPATH"
/Users/david/.hermes/hermes-agent/venv/bin/python -m pytest /Users/david/.medit/tests/ \
    --rootdir=/Users/david/.medit/tests "$@"
```

**任何 hermes 项目跑 pytest 必须用 venv python**. 系统 python 在 venv 存在时 fallback, 行为可能不同.

## 9. 关键 Learnings (给 next session)

1. **Reasoning before implementation** — 用户说 "推理最佳路径" 时, 必须先 reasoning 输出 P0/P1/P2, 再 implement
2. **P0/P1/P2 = Impact × Confidence ÷ Effort** — 不是按"重要性"排序, 是按 ROI 排序
3. **P2 跳过要写理由** — "跳过 P2-1 Radix tree: N < 100" 比 "P2 暂不实施" 强 100 倍
4. **Bridging OPT** — 算法做完 ≠ 落地. 必须有 5 个 bridging OPT (wrapper/integration/perf/deterministic/e2e)
5. **Acceptance demo script** — 1 键真实产出展示, 不是 "tests passed"
6. **State pollution after demo** — 跑完 demo 必须重置 state 再跑 regression test
7. **Pytest venv pinning** — `run_all.sh` 必须硬编码 venv python, 系统 python 行为不同
8. **107 tests 一次过** — 双轨 + 状态独立 + 真实 e2e = 一次过 100+ tests 不奇怪
